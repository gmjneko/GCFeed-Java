# 08 前端适配方案

前端复用原项目的 `console/`（React 18 + Vite 5），**改动很小**：接口路径、请求参数、响应字段名全部保持不变，唯一的必要改动是适配 `ApiResponse` 包装。

> 当前 `apiRequest` 已完成成功响应解包，并兼容 Go 裸响应；六个 user 接口已实现，其他模块仍待迁移。下文保留改造前后的设计对照。

## 2. 需要改的地方：只有一处

`App.jsx` 底部的 `apiRequest` 函数是全前端唯一的 HTTP 出口，**只改这一个函数**即可完成适配。

### 2.1 现状

```js
async function apiRequest(path, options = {}) {
  const headers = {
    Accept: "application/json",
    ...(options.headers || {})
  };
  if (options.body) headers["Content-Type"] = "application/json";
  if (options.token) headers.Authorization = `Bearer ${options.token}`;

  const response = await fetch(path, {
    method: options.method || "GET",
    headers,
    body: options.body ? JSON.stringify(options.body) : undefined
  });

  if (!response.ok) {
    let message = "请求失败";
    try {
      const data = await response.json();
      if (data.error) message = data.error;
      if (data.message) message = data.message;
    } catch {
      message = response.statusText || message;
    }
    const error = new Error(message);
    error.status = response.status;
    throw error;
  }

  if (response.status === 204) return null;
  return response.json();
}
```

### 2.2 改造后

```js
async function apiRequest(path, options = {}) {
  const headers = {
    Accept: "application/json",
    ...(options.headers || {})
  };
  if (options.body) headers["Content-Type"] = "application/json";
  if (options.token) headers.Authorization = `Bearer ${options.token}`;

  const response = await fetch(path, {
    method: options.method || "GET",
    headers,
    body: options.body ? JSON.stringify(options.body) : undefined
  });

  // 204 与 201 都可能有响应体，先尝试解析
  let payload = null;
  if (response.status !== 204) {
    try {
      payload = await response.json();
    } catch {
      payload = null;
    }
  }

  // 统一响应体：{ code, message, data }
  // code !== 0 表示业务失败，此时 HTTP 状态码也一定非 2xx
  if (!response.ok || (payload && payload.code !== 0)) {
    const message = (payload && (payload.message || payload.error)) || "请求失败";
    const error = new Error(message);
    error.status = response.status;
    error.code = payload ? payload.code : undefined;
    throw error;
  }

  // 成功：返回业务数据，调用方感知不到包装层
  return payload ? payload.data : null;
}
```

### 2.3 关键设计：在出口处解包

**为什么在 `apiRequest` 里解包 `data`，而不是让每个调用点自己解**：

前端有 26 个调用点，模式是 `const data = await apiRequest(...)` 然后直接用 `data.xxx`。如果在 `apiRequest` 里返回整个 `payload`，26 个调用点都要改成 `payload.data.xxx`。

在出口处统一解包，**调用方的代码一行都不用改**。这是适配成本最低的方案。

### 2.4 保留 `error.status`

```js
error.status = response.status;
```

前端的 401 处理依赖它：

```js
catch (error) {
  if (error.status === 401) {
    session.clearAuth();
    onNavigate("/auth");
  }
}
```

这段逻辑有十几处，不要改动。

**新增 `error.code`**（可选）：前端可以按业务码做更精确的提示，例如：

```js
if (error.code === 10011) {
  setMessage("该账号已被注册，请换一个");
} else {
  setMessage(error.message || "注册失败");
}
```

这不是必须的，但既然后端提供了稳定错误码，前端可以用来改善交互。

### 3.4 时间格式（需要确认但大概率无感）

| 版本 | 格式示例 |
| --- | --- |
| Go | `2026-05-04T12:00:00Z`（RFC3339Nano） |
| Java | `2026-05-04 12:00:00` |

前端的时间处理：

```js
function formatRelativeTime(value) {
  const date = new Date(value);
  // ...
}
```

`new Date("2026-05-04 12:00:00")` 在**大多数浏览器**中能正确解析，但这个格式严格来说不是 ISO 8601（缺少 `T`），Safari 早期版本可能返回 `Invalid Date`。

**建议**：后端配置 Jackson 输出 ISO 格式，彻底避免浏览器兼容性问题：

```yaml
spring:
  jackson:
    date-format: yyyy-MM-dd'T'HH:mm:ss
    time-zone: Asia/Shanghai
```

或者更稳妥：前端改成显式解析。

```js
function parseDate(value) {
  if (!value) return null;
  // 兼容 "2026-05-04 12:00:00" 与 ISO 格式
  return new Date(String(value).replace(" ", "T"));
}
```

**建议两处都做**：后端输出 ISO 格式（规范），前端做兼容处理（健壮）。成本都很低。

## 4. 上传接口的特殊处理

`UploadPage` 的上传**不走 `apiRequest`**，是直接 `fetch`：

```js
async function uploadFile(file, kind, token) {
  const formData = new FormData();
  formData.append("file", file);
  formData.append("kind", kind);

  const response = await fetch("/api/uploads", {
    method: "POST",
    headers: { Authorization: `Bearer ${token}` },
    body: formData
  });
  // ...
  return response.json();
}
```

**这里需要单独适配**。找到 `uploadFile` 函数（约在 `App.jsx:2400` 附近），改为解包 `data`：

```js
const payload = await response.json();
if (!response.ok || payload.code !== 0) {
  throw new Error(payload.message || "上传失败");
}
return payload.data;   // { url, kind, filename, size }
```

调用方用的是 `uploaded.url`，因此返回 `data` 后调用代码不用改。

**建议顺手重构**：把上传也改成走 `apiRequest` 的能力（`apiRequest` 目前不支持 `FormData`，需要在里面加一个判断——`body` 是 `FormData` 时不设 `Content-Type` 也不 `JSON.stringify`）。这样只需要维护一套请求逻辑。

## 6. 前端行为约定（后端需要保证的部分）

前端有一些行为假设，后端必须满足，否则前端会出错。

### 6.1 列表永远是数组

```js
const nextComments = data.items || [];
setComments(nextComments);
```

前端虽然写了 `|| []` 兜底，但后端必须返回 `[]` 而非 `null`。Java 中要显式初始化：

```java
List<FeedItemVO> items = new ArrayList<>();   // ✅ 序列化为 []
// 不要这样：
List<FeedItemVO> items = null;                // ❌ 序列化为 null
```

### 6.2 计数以接口返回值为准

```js
const data = await apiRequest(`/api/videos/${current.video_id}/like`, { ... });
setLiked((state) => ({ ...state, [current.video_id]: Boolean(data.active) }));
updateCurrentItem(current.video_id, { like_count: data.like_count ?? current.like_count });
```

前端**不做乐观更新**，`await` 服务端结果后才回写。因此后端响应里的 `active` 和 `like_count` 必须是**操作后的准确值**。

具体含义：`active` 来自本次事务里实际写入的行为状态；计数采用最终一致的异步刷库，所以响应计数 = 已落库值 + Redis 中尚未刷库的增量 + 本次请求的变化（钳制非负）。这样操作者看到的数字立即包含自己的点赞；其他用户在 Feed 和详情里最多晚一个刷库周期看到。

### 6.3 评论数在创建响应里返回

```js
const data = await apiRequest(`/api/videos/${current.video_id}/comments`, { ... });
// data.comment_count 用于刷新计数
```

发表评论的响应必须包含 `comment_count`，且是**自增后的最新值**。

### 6.4 关注接口返回 `following` 而不是 `active`

```js
const data = await apiRequest(`/api/users/me/following/${authorID}`, { ... });
setFollowing((state) => ({ ...state, [authorID]: Boolean(data.following) }));
updateSessionRelationCount(session, data.following_count);
```

字段名是 `following`（布尔），**与点赞/收藏的 `active` 不同名**。后端要注意这个差异。

### 6.5 空数组表示全部已读

```js
function markMessagesRead(token, ids = []) {
  return apiRequest("/api/messages", {
    method: "PATCH",
    token,
    body: { message_ids: ids }
  });
}
```

默认参数是 `[]`，语义是「全部标记已读」。后端必须把空数组当作「全部」而不是「一条都不标记」。

**这是原项目的产品行为**，本版本保留。如果将来要改成更明确的契约（比如 `mark_all: true`），需要前后端一起改。

### 6.6 幂等键每次点击都新生成

```js
headers: {
  "Idempotency-Key": `web-like-${current.video_id}-${Date.now()}`
}
```

带时间戳意味着**每次点击都是新键**，幂等只在「同一次请求被重试」时生效。这是正确的用法 —— 用户连点两次点赞，第二次是取消点赞，应该有不同语义。

后端不要因为「同一用户短时间内的操作」就判定为重复请求。

### 6.7 401 的统一处理

```js
if (error.status === 401) {
  session.clearAuth();
  onNavigate("/auth");
}
```

后端所有鉴权失败必须返回 **401**（不是 403），否则前端不会清空登录态。

| 场景 | 应返回 |
| --- | --- |
| 无 `Authorization` 头 | 401 |
| 令牌格式错误 | 401 |
| 令牌过期 | 401 |
| 令牌已吊销（登出后） | 401 |
| 令牌合法但权限不足 | **403** |

