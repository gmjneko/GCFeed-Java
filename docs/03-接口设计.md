# 03 接口设计

## 1. 通用约定

### 1.1 统一响应体

所有接口（除 `/uploads/**` 静态文件外）返回统一结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | 业务码，`0` 表示成功，非 0 见错误码表 |
| `message` | string | 成功固定为 `ok`；失败为可读原因 |
| `data` | object / array / null | 业务数据，失败时为 `null` |

**HTTP 状态码同时保持语义正确**（400 / 401 / 403 / 404 / 409 / 500），这样网关、监控、日志统计能直接按状态码分类，前端也能用状态码做通用分支（如 401 跳登录页）。

具体错误码定义见 [04 技术基础设施设计](04-技术基础设施设计.md) 的错误码章节。

### 1.2 鉴权

| 方式 | 请求头 | 适用 |
| --- | --- | --- |
| 用户令牌 | `Authorization: Bearer <access_token>` | `/api/**` |
| 服务令牌 | `X-Internal-Token: <token>` | `/internal/**` |

接口的鉴权强度由 Controller 方法上的注解决定：

| 注解 | 语义 | token 缺失 | token 非法 |
| --- | --- | --- | --- |
| `@RequireAuth` | 必须登录 | 401 | 401 |
| `@OptionalAuth` | 可选登录 | 放行（匿名） | 放行（匿名） |
| 无注解 | 完全公开 | 放行 | 放行 |

### 1.3 重复提交键

支持短时重复提交拦截的写接口可接收 `Idempotency-Key` 请求头（可选，去首尾空白后最长 128 字符）。

- 相同用户、操作和请求键在 3 秒窗口内再次提交，返回 `409` / `code = 80002`；空键视为未提供。
- Redis 只保存短时占用标记，不保存参数指纹或响应结果。窗口结束后的请求会重新进入业务逻辑。
- 发布的可靠去重由 `video.uk_author_idempotency` 和业务字段比对负责；互动的重复计数由业务状态机、唯一约束和事务负责。
- 这不是网络超时后的结果重放机制。鉴权仍在进入 Service 前完成。

### 1.4 分页

系统内有两种分页，**不要混用**：

| 方式 | 适用 | 请求参数 | 响应字段 |
| --- | --- | --- | --- |
| **游标分页** | Feed、评论、消息、关注/粉丝列表 | `cursor` + `limit` | `items` + `next_cursor` + `has_more` |
| **游标分页** | 用户作品列表 | `cursor` + `limit` | `items` + `next_cursor` + `has_more` |

游标分页的通用结构：

```json
{
  "items": [],
  "next_cursor": "",
  "has_more": false
}
```

约定：

- `items` 为空时是 `[]`，**不是 `null`**。
- 本页为空时 `next_cursor` 为 `""`，`has_more` 为 `false`。
- `has_more` 的实现是「多查一条」：查 `limit + 1` 条，多出来说明还有下一页，然后截断到 `limit`。
- `limit` 默认值各接口不同，上限统一 **100**；显式传 `0` 或负数返回 400（不是取默认值），超过 100 则静默截断。

游标是 URL-safe Base64 编码（无 padding）的不透明字符串，客户端**不应解析**，只需原样回传。当前作品列表和 Timeline 使用 `LocalDateTime.toString()|videoId` 的 UTF-8 编码，保留完整时间精度并兼容已有视频游标；其他列表的 JSON 游标属于后续设计。

### 1.5 时间格式

统一 `yyyy-MM-dd HH:mm:ss`，例如 `"2026-05-04 12:00:00"`。

## 3. 账户模块

### 3.1 注册

```
POST /api/users
```

请求体：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `account` | string | 是 | 去空格后 1..64 字符，全局唯一 |
| `password` | string | 是 | 去空格后非空，最长 64 字符且 UTF-8 不超过 72 字节 |
| `nickname` | string | 是 | 去空格后非空，最长 64 字符 |

```json
{
  "account": "tester",
  "password": "secret123",
  "nickname": "测试用户"
}
```

响应 `201`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 42,
    "account": "tester",
    "nickname": "测试用户",
    "avatar_url": null,
    "bio": null,
    "status": 1,
    "role": "user",
    "following_count": 0,
    "follower_count": 0,
    "work_count": 0
  }
}
```

**业务规则**

- 账号重复返回 `409` / `code = 10011`（`account already exists`）。不接入 `Idempotency-Key`，也不重放已有账号资料。
- 密码只存 BCrypt 哈希，响应中绝不返回密码字段。
- 新用户默认 `status = 1`、`role = user`，并初始化一行 `user_relation_stat`。

### 3.2 登录

```
POST /api/sessions
```

请求体：

| 字段 | 类型 | 必填 |
| --- | --- | --- |
| `account` | string | 是 |
| `password` | string | 是 |

响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiJ9...",
    "token_type": "Bearer",
    "expires_in_seconds": 900
  }
}
```

**业务规则**

- 账号不存在与密码错误**返回同一个错误**（`401` / `code = 10012` `invalid credentials`），避免账号枚举攻击。原 Go 实现也做了这个转换（`ErrUserNotFound` → `ErrInvalidCredentials`）。
- `status != 1`（冻结/注销）的账号拒绝登录，返回 `403` / `code = 10013`。
- 令牌有效期默认 900 秒（15 分钟），与 Go 版 `access_ttl: 15m` 一致。

**JWT 声明结构**

| 声明 | 含义 |
| --- | --- |
| `uid` | 用户 ID |
| `role` | 用户角色 |
| `token_type` | 固定 `access` |
| `jti` | 令牌唯一标识（16 字节随机 hex） |
| `iat` / `exp` | 签发 / 过期时间 |
| `iss` | 签发者，固定 `gcfeed` |

### 3.3 登出

```
DELETE /api/sessions/current
```

响应 `204 No Content`（无响应体）。

**业务规则**：把令牌的 `jti` 写入 Redis 黑名单，TTL 等于令牌剩余有效期。重复登出同一 token 返回 401（已经吊销），不会延长黑名单 TTL。Redis 不可用时受保护请求失败，不放行已吊销令牌。

> 原 Go 实现只返回 204，服务端不失效令牌 —— 令牌在有效期内仍可用。本版本改为真正的服务端吊销。

### 3.4 当前用户资料

```
GET /api/users/me
```

响应 `200`：同注册响应结构（`UserVO`）。

### 3.5 更新资料

```
PATCH /api/users/me
```

请求体（**全部字段可选，指针语义：不传的字段保持原值**）：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `nickname` | string | 若传则去空格后非空，最长 64 |
| `avatar_url` | string | 最长 512 |
| `bio` | string | 最长 255 |

```json
{
  "nickname": "新昵称",
  "bio": "做点小东西"
}
```

响应 `200`：更新后的 `UserVO`。

**业务规则**

- 三个字段全部为 `null` 时返回 `400` / `code = 10009`（`profile update is required`）。
- 这是**部分更新**语义：只有显式传入的字段会被改写，未传字段保持原值。因此 DTO 用包装类型（`String` 而非 `String` 带默认值），靠 `null` 区分「未传」与「传了空串」。
- `nickname` 传空串返回 `400`（昵称不能清空）。
- `avatar_url` / `bio` 传空串清空对应字段。无需幂等键；重复赋值不创建额外资源，也不修改未传入的字段。

### 3.6 公开用户资料

```
GET /api/users/{userId}
```

响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 42,
    "nickname": "测试用户",
    "avatar_url": null,
    "bio": null,
    "following_count": 18,
    "follower_count": 42,
    "work_count": 5
  }
}
```

**与 `/api/users/me` 的差别**：公开资料是 `PublicUserVO`，**不返回 `account`、`role`、`status`**，避免泄露账号名和账号状态。

用户不存在返回 `404` / `code = 10010`。

## 4. 视频模块

### 4.1 发布视频

```
POST /api/videos
Idempotency-Key: <可选>
```

请求体：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `title` | string | 是 | 去空格后非空，最长 128 |
| `description` | string | 否 | 最长 512 |
| `media_url` | string | 是 | 非空，最长 512 |
| `cover_url` | string | 是 | 非空，最长 512 |

响应 `201`（首次创建）/ `200`（视频表业务键命中已有视频）：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 103,
    "author_id": 42,
    "title": "标题",
    "description": "简介",
    "media_url": "/uploads/video/xxx.mp4",
    "cover_url": "/uploads/cover/xxx.jpg",
    "status": 2,
    "like_count": 0,
    "comment_count": 0,
    "favorite_count": 0,
    "published_at": "2026-05-04 12:00:00",
    "created_at": "2026-05-04 12:00:00",
    "updated_at": "2026-05-04 12:00:00"
  }
}
```

**业务规则**

- **创建即发布**：新视频直接置 `status = 2`（上线）并写 `published_at`，当前无草稿流程。
- 同一事务内创建 `video` 与 `video_stat` 两行。
- 可选 `Idempotency-Key` 在 Redis 中提供 3 秒重复提交拦截。可靠去重由视频表唯一约束 `(author_id, idempotency_key)` 完成；再次提交同一键时读取已有视频，标题、简介、媒体地址或封面不一致返回 `409` / `code = 20010`。首次创建返回 `201`，已有视频返回 `200`。不保存或重放历史 HTTP 响应。

### 4.2 视频详情

```
GET /api/videos/{videoId}
```

响应 `200`：同发布响应的结构。

**业务规则**：只返回 `status = 2`（上线）的视频。不存在或未上线都返回 `404` / `code = 20008`。

### 4.3 删除视频

```
DELETE /api/videos/{videoId}
```

响应 `204 No Content`。

**业务规则**

- **只有作者本人能删除**。非作者返回 `403` / `code = 20009`。
- 软删除：只把 `status` 改为 `4`，行保留。
- 重复删除返回 `204`（幂等）。该幂等性由 Service 查询已删除状态后直接成功实现，删除接口不依赖或保存 `Idempotency-Key`。

### 4.4 我的作品

```
GET /api/users/me/videos?limit=20&cursor=
```

| 参数 | 类型 | 默认 | 约束 |
| --- | --- | --- | --- |
| `limit` | int | 20 | > 0，上限 100 |
| `cursor` | string | 空 | 上一页响应的 `next_cursor`，非法游标返回 400 |

响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [ /* VideoVO 数组 */ ],
    "next_cursor": "eyJ...",
    "has_more": true
  }
}
```

**业务规则**：返回当前用户的 `status IN (2, 3)` 视频 —— **下架的视频作者自己仍能看到**。结果按 `published_at DESC, id DESC` 排序，使用这两个字段组成稳定游标。

### 4.5 作者的公开作品

```
GET /api/users/{userId}/videos?limit=20&cursor=
```

参数和响应格式同“我的作品”，只返回 `status = 2` 且未删除的公开作品，按 `published_at DESC, id DESC` 使用游标翻页。

> 作品列表使用游标分页，不再使用 offset。服务端每次多取一条记录计算 `has_more`，`next_cursor` 是本页最后一条视频的发布时间和 ID 编码。

## 5. 上传模块

### 5.1 上传文件

```
POST /api/uploads
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `file` | file | 是 | 文件内容 |
| `kind` | string | 否 | `video` / `cover` / `avatar` / `file`，默认为 `file` |

响应 `201`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "url": "/uploads/video/1735824000123456789-a1b2c3d4e5f6.mp4",
    "kind": "video",
    "filename": "1735824000123456789-a1b2c3d4e5f6.mp4",
    "size": 10485760
  }
}
```

**文件类型与大小约束**

| `kind` | 允许扩展名 | 允许 MIME | 大小上限 |
| --- | --- | --- | --- |
| `video` | `.mp4` `.mov` `.webm` | `video/mp4` `video/quicktime` `video/webm` `application/octet-stream` | 512 MiB |
| `cover` | `.jpg` `.jpeg` `.png` `.webp` | `image/jpeg` `image/png` `image/webp` | 20 MiB |
| `avatar` | 同上 | 同上 | 20 MiB |
| `file` | 不校验 | 不校验 | 1 GiB |

视频额外校验（需要 `ffprobe`）：

- 时长 > 0 且 <= 600 秒
- 宽高均 > 0 且 <= 3840
- 视频编码 ∈ `h264 h265 hevc vp8 vp9 av1`
- 音频编码 ∈ `aac mp3 opus vorbis`

MP4 / MOV 上传后执行 `faststart`（`ffmpeg -c copy -movflags +faststart`），把元数据前置以支持边下边播。

**文件名规则**：`{纳秒时间戳}-{12位随机hex}{扩展名}`，避免同名冲突。

**存储目录**：`{gcfeed.upload.root}/{kind}/{filename}`，只有一层分类目录，不按用户或日期分片。

**校验失败的降级**：`ffprobe` / `ffmpeg` 不可用时返回 `500` / `code = 90010`；其余校验失败返回 `400`。校验不通过时删除已落盘的文件。

> 原 Go 实现把 `ffmpeg` 的 stderr 拼进错误响应，可能泄露工具版本与路径信息。本版本改为服务端记日志，对外统一文案。

## 6. 互动模块

### 6.1 点赞 / 取消点赞

```
PUT    /api/videos/{videoId}/like
DELETE /api/videos/{videoId}/like
Idempotency-Key: <可选>
```

无请求体。响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "video_id": 103,
    "action_type": "LIKE",
    "active": true,
    "like_count": 18,
    "favorite_count": 7
  }
}
```

**鉴权**：四个互动写接口均要求登录。`PUT` = 设为生效，`DELETE` = 设为取消。**不是切换**，因此重复 `PUT` 不会来回翻转。

请求键可选，四个操作分别使用 `interaction.like`、`interaction.unlike`、`interaction.favorite`、`interaction.unfavorite` scope。Redis 在 3 秒内拦截相同用户、操作和键的重复提交；键过期后重新执行并返回当前状态。无键请求也正常执行。持久化业务幂等由 `(user_id, video_id, action_type)` 唯一约束、条件更新和“状态变化时才产生计数增量”保证，不重放旧响应。

**业务规则**

| 场景 | `active` | `like_count` |
| --- | --- | --- |
| 首次 PUT | `true` | +1 |
| 重复 PUT | `true` | 不变 |
| 取关后重新 PUT | `true` | +1 |
| 首次 DELETE | `false` | 不变（不写入行为行） |
| 取消已生效的点赞 | `false` | -1 |
| 重复 DELETE | `false` | 不变 |

- 视频必须存在且 `status = 2`，否则 `404`。
- 计数只在行为从未生效变为生效，或从生效变为取消时变化；`active` 是强一致的，计数是最终一致的。
- 响应中的 `like_count` / `favorite_count` = 已落库值 + 尚未刷库的增量 + 本次变化，钳制非负，点赞后可直接用于刷新按钮。
- Feed 与视频详情立即反映 `active` 状态；其中的计数读已落库值，最多落后一个刷库周期（默认 2 秒）。
- 同一请求键在短时窗口内再次提交会返回 409；窗口之外按业务当前状态处理。
- 当前没有发布 RabbitMQ 事件、写热榜或发送点赞通知。仅在状态实际变化处保留 TODO：未来通过 Outbox 或可靠的事务提交后机制发布 `interaction.action_changed`，消费者需处理幂等、重试、死信，再接热榜和通知（自己点赞自己不通知）。

### 8.1 拉取 Feed（Timeline 已实现）

当前仅实现 `GET /api/feed-items` 的 `timeline` 场景，直接查询数据库，不使用 Feed 缓存。`hot`、`following`、`recommend` 均返回 `400 / 70003`，下方其他场景描述为后续规划。

```
GET /api/feed-items?scene=timeline&cursor=&limit=10
```

| 参数 | 类型 | 默认 | 约束 |

| `scene` | string | `timeline` | 当前仅支持 `timeline`，其余场景待实现 |

响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "scene": "timeline",
    "items": [
      {
        "video_id": 103,
        "author_id": 42,
        "author_nickname": "测试用户",
        "author_avatar_url": null,
        "title": "标题",
        "description": "简介",
        "media_url": "/uploads/video/xxx.mp4",
        "cover_url": "/uploads/cover/xxx.jpg",
        "like_count": 18,

```

**各 scene 的语义**

| scene | 排序 | 游标内容 | 登录要求 |
| --- | --- | --- | --- |
| `timeline` | `published_at DESC, id DESC` | URL-safe Base64 的 `发布时间\|视频ID` | 可选（匿名返回 `liked`/`favorited` 均为 `false`） |
| `hot` | 热度分倒序 | 见下方 | 可选 |
| `following` | `published_at DESC, id DESC` | `{published_at, video_id}` | **必须**，未登录返回 401 |
| `recommend` | 推荐排序分倒序 | `{rank_score, published_at, video_id}` | **必须**，未登录返回 401 |

`scene` 归一化规则：去空格 + 转小写；空值取默认 `timeline`；未注册的值返回 `400` / `code = 70003`。

**`liked` / `favorited` 字段**：仅当请求携带有效 token 时才会是 `true`，匿名请求固定为 `false`。前端用它初始化点赞/收藏按钮的选中态。

**hot 场景的游标有两种形态**

| 形态 | 触发条件 | 内容 |
| --- | --- | --- |
| 窗口形态 | Redis 可用 | `{window_end, offset}` |
| 仓储形态 | Redis 不可用，降级查 MySQL | `{hot_score, published_at, video_id}` |

窗口形态下 `window_end` 在翻页期间**锚定不变**，用 `offset` 增量翻页 —— 保证一次翻页过程中热榜不会滑动导致数据重复或丢失。

**当前 Timeline 行为**

- 只返回 `status = 2` 且 `published_at IS NOT NULL` 的视频；相同发布时间按 ID 倒序。
- 每次多取一条判断 `has_more`，非空末页也返回 `next_cursor`；空页返回 `items=[]`、`next_cursor=""`、`has_more=false`。
- 作者缺失或已注销（`account.status = 3`）时，视频仍保留，昵称和头像返回 `null`；统计行缺失时三个计数均为 0。
- 有效 token 下批量查询当前用户 `interaction_action` 中 `status=1` 的 `LIKE/FAVORITE`。取消态和其他用户的行为不生效。
- 无 token、无效或已吊销 token 按 `@OptionalAuth` 视为匿名，`liked/favorited` 均为 `false`。互动写接口要求登录，使用独立幂等 scope；Feed 不会因请求重放覆盖较新的互动状态。
- `published_at` 展示格式为 `yyyy-MM-dd HH:mm:ss`；游标内时间保留数据库精度。

## 10. 播放优化模块

### 10.1 播放参数

- `platform`：去空格；空值 → `Web`。**不做大小写归一**（`web` 与 `Web` 是两条不同记录）。
- `network_type`：去空格；空值 → `DEFAULT`；`wifi` / `wi-fi` → `WiFi`；`3g`/`4g`/`5g` → 大写；其他值转大写后原样查询。

**结果钳制**：`preload_count <= 0` → 3，`> 10` → 10；`buffer_ms <= 0` → 1200。

```json
        "published_at": "2026-05-04 12:00:00"
      }
    ],
    "next_cursor": "...",
    "has_more": true
  }
}
```

`reason` 取值：`interest_match`（有用户向量且相似度 > 0.05）/ `hot`（热度 > 0）/ `fresh`（其他）。

排序与打分算法见 [05 模块功能设计](05-模块功能设计.md) 的推荐章节。

### 11.2 曝光去重判定

```
POST /internal/exposure-decisions
X-Internal-Token: <token>
```

请求体：

| 字段 | 类型 | 必填 |
| --- | --- | --- |
| `user_id` | long | 是 |
| `scene` | string | 是 |
| `request_id` | string | 否 |
| `video_ids` | long[] | 是 |

响应 `200`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "user_id": 42,
    "scene": "recommend",
    "decisions": [
      { "video_id": 1, "allowed": false, "reason": "recently_exposed", "last_exposed_at": "2026-05-03 10:00:00" },
      { "video_id": 3, "allowed": true,  "reason": "fresh" }
    ]
  }
}
```

**判定窗口**：最近 7 天内曝光过 → `allowed = false`。

返回顺序与去重后的输入 `video_ids` 顺序一致。`video_ids` 为空时直接返回空数组，不查库。

### 11.3 批量写入曝光

```
POST /internal/exposures
X-Internal-Token: <token>
```

请求体同 11.2。响应 `201`：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "exposures": [
      {
        "user_id": 42,
        "video_id": 1,
        "first_exposed_at": "2026-05-04 12:00:00",
        "last_exposed_at": "2026-05-04 12:00:00",
        "exposure_count": 2,
        "last_scene": "recommend"
      }
    ]
  }
}
```

**语义**：批量幂等写入。服务端按 `video_id` 去重（保留首次出现顺序），每个视频写一行流水 + upsert 一行聚合，**整个批次在同一事务内**；任一视频不存在或未上线则 `404` 并整批回滚。
